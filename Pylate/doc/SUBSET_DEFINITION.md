# The admitted subset, and why each rejection exists

Pylate rejects 40 named constructs. This document gives the reason for each. The
list is generated by `Syntax/Check.lean` and `Syntax/ClassTable.lean`; every rule
here is a string those files emit, and every one has a corpus program that pins
it.

## The one argument behind almost all of it

Pylate's output is data, and what consumes it lowers the program into **Laurel**
composites over a closed value datatype. A composite declaration fixes an object's
fields; a datatype fixes the universe of values.

That is where the leverage comes from, and also the obligation:

> Every shape invariant baked into a composite declaration or a value constructor
> is an **assumption**. If the program can break it at runtime, the encoding is
> unsound. So the subset must reject the constructs that could.

Python permits all of them — field addition and deletion, monkey-patching,
retyping an object in place. So each rejection below names one invariant and the
construct that would falsify it. The subset is not a list of features someone did
not get to; it is the precondition of the encoding.

Two consequences worth stating plainly. Rejection is **not** the same as a
soundness gap: a rejected program gets no answer, which is honest. And rejection
is a *schedule* — several rules below say what would lift them, and
`ALGORITHM_AND_SOUNDNESS.md` explains why an early admission would be caught
downstream rather than silently believed.

## 1. An object's shape is fixed by its declaration

The composite has the fields the class declares. Anything that adds, removes or
retypes a field at runtime invalidates it.

| rule | rejected | why |
| --- | --- | --- |
| `shape-mutation` | `del` on an attribute or a subscript | deleting a field removes one the composite has |
| `shape-store` | an attribute store to `__class__`, `__dict__`, `__bases__`, `__mro__` or `__slots__`, anywhere; and a store to any name that is neither a field nor a property setter on some admitted class | the first group names the dispatch machinery rather than a field: `__class__` retypes a live object so its tag stops being constant, `__bases__` rewrites an already-derived resolution order, `__dict__` replaces the schema wholesale. The second group has nowhere to land — the composite is derived from the declaration, so a field no class declares does not exist in it. `storableAttrs` in `Check.lean` builds the permitted set |
| `hook-override` | `__getattr__`, `__getattribute__`, `__setattr__`, `__delattr__`, `__new__` | *"overriding the attribute/creation protocol is outside the subset."* With these, attribute syntax stops meaning field access: two reads of the same name can return different types, which voids the composite-field model entirely. `__new__` can also return an instance of another class |
| `banned-builtin` | `setattr`, `getattr`, `hasattr`, `delattr`, `vars`, `id`, `type`, `super`, `globals`, `locals`, `eval`, `exec`, `compile`, `__import__`, `open`, `input`, `breakpoint`, `classmethod`, `staticmethod`, `property`, `memoryview` | each is a dynamic escape from one-step dispatch. `vars`/`__dict__` access can replace an object's shape wholesale; `id` is discussed in §4. `super` is the one entry with an admitted shape carved out of it — see §8 |
| `class-body-stmt` | a method in a `TypedDict` | *"a TypedDict declares fields only."* A TypedDict is a dict at runtime, so shape is transient; admitting methods would imply an object model it does not have |

### Measured: what the two rules closed

The invariant this section claims — *an object's shape and a class's MRO are fixed
by their declarations* — is what the Laurel encoding assumes. Thirty-one ways to
break it were run through the analyzer, comparing its claim against a live CPython
run. Four were wrong. `shape-store` and `duplicate-class` were added for them, and
each row below is now a rejection with a corpus case pinning it.

| was wrong | measured before the rule | now |
| --- | --- | --- |
| `o.__class__ = D` | `a.__class__ = B; r = a.m()` → `r = int lit=1`, CPython `2`. A non-aborting `attr-missing` obligation, so the retag was ignored and dispatch resolved to the old class | `shape-store` |
| `o.__dict__ = {}` | then `r = a.n` → `r = int lit=0`, CPython `AttributeError` | `shape-store` |
| `o.zz = 5` (undeclared) | Pylate and CPython agreed on `5`; wrong only against the *encoding's* composite | `shape-store` when no class declares `zz`; otherwise an error edge at the store — see below |
| `class C` declared twice | `class E(KeyError)` then `class E(ValueError)`, `raise E("x")` → routed to `except KeyError`, CPython takes `except ValueError`. **No obligation at all**: `ClassTable` is an assoc list and the first declaration wins, so the second was invisible | `duplicate-class` |

The first three shared one cause, documented at `Transfers/Objects.lean:193-203`: a
store outside the layout wrote the cell and filed `attr-missing` without raising,
because going straight to `AttributeError` claimed a *guaranteed* error on
`o.y = 2; v = o.y`, which CPython answers with `2`. The original reasoning was
right about CPython and wrong about the encoding. The resolution is split: an
**admission** rule for a name no class declares, and at the store an **error edge**
whose strength depends on the receiver, since only the receiver's class decides
whether CPython can hold the field at all. The next section is that split.

Two things the rule deliberately does not do. A store through `self` is exempt,
because `buildClassTable` derives a layout from every `self.f` store in the
class's methods, so such a store names a layout field by construction. And a
store through a property setter is permitted, since it runs the setter rather
than writing a cell — without that exemption `console.panel.gauge.reading = v`
was rejected, which is the one false positive the corpus caught.

### Undeclared attributes: two strengths, and why this is the mainstream reading

Admission cannot know a receiver's class, so `shape-store` checks the union over
all classes: it refuses a name that is a field or setter on *no* admitted class.
A name that some *other* class declares gets through, and the analysis decides it
per receiver — which it can do, because by then the class is known.

Python is permissive here and the type checkers are not. Measured on
`p.zz = 5` where `zz` is not `Plain`'s field:

| | CPython | mypy | ty | pyright |
| --- | --- | --- | --- | --- |
| plain class | **allowed**, `zz` added | `"Plain" has no attribute "zz"` | `unresolved-attribute` | `Cannot assign to attribute "zz"` |
| `__slots__` class | `AttributeError` | error | error | error |
| `@dataclass(frozen=True)` | `FrozenInstanceError` | error | error | error |

So treating an undeclared write as an error is not a strict reading of the
subset: all three checkers already do it, and none of them models the runtime's
permissiveness. What the runtime *does* decide is whether the error is certain,
and that is exactly the distinction the analysis carries:

| receiver | store outside the layout | why |
| --- | --- | --- |
| slots-complete over its MRO, or a frozen dataclass | **guaranteed error** — `AttributeError` / `FrozenInstanceError`, no normal edge | there is no `__dict__` to hold the field, so CPython always raises |
| any other class | **maybe error** — `attr-missing` plus an `AttributeError` edge, and the store also happens | CPython permits it, so the raise cannot be claimed; but the site is an error to every type checker and the composite has no slot for it, so it is not passed over silently |

Reads need no such split: a read of a field the receiver's class lacks is a
`guaranteed-error` either way, because CPython raises whether or not slots are
declared. And a field *inherited* from a superclass resolves exactly, diamonds
included, since `buildClassTable` unions the layout over the whole MRO.

### `__slots__`

Admitted in a class body — the one assignment a class body may carry, because it
is a declaration rather than class-level state. It is what lets a program opt into
the guaranteed strength above.

| rule | rejected | why |
| --- | --- | --- |
| `slots-mismatch` | a field the class assigns that no `__slots__` on its MRO declares | CPython raises `AttributeError` the moment `__init__` runs, so the class can never be constructed. mypy agrees (*"Trying to assign name `m` that is not in `__slots__`"*); ty misses it |

Slots-completeness is **MRO-wide**, and measured to need to be:

| | has `__dict__` | `o.zz = 5` |
| --- | --- | --- |
| `Slotted` with `__slots__ = ("n",)` | no | `AttributeError` |
| a subclass declaring nothing | **yes** | **allowed — the guarantee is gone** |
| a subclass declaring `__slots__ = ()` | no | `AttributeError` |

One omitted declaration anywhere on the chain restores `__dict__`, so the
analysis downgrades that receiver to the maybe strength rather than claiming an
error CPython would not raise. Two conditions come free from CPython: a
slots/`__init__` mismatch fails at construction (hence the rule above), and
mixing in a `__dict__`-bearing base is refused at class creation
(`multiple bases have instance lay-out conflict`). A non-`object` builtin on the
chain also disqualifies, since `BaseException` instances carry a `__dict__`.

Slots are **not** required. Plain classes stay admitted, at the maybe strength;
requiring `__slots__` everywhere would buy runtime enforcement that a verifier —
which never runs the program — does not need, at the cost of every class and
every subclass having to declare and maintain one.

### Measured: what does hold

Most of what looks accepted at admission **aborts** during analysis, which is a
conservative refusal rather than a hole. Worth recording, because the admission
verdict alone is misleading:

| construct | analysis result |
| --- | --- |
| `C.m = f`, `C.newattr = 5`, `C.__bases__ = (Q,)` | abort `AttributeError` — none is a declared field of the class object |
| `o.__dict__['x'] = v` | abort `AttributeError` on reading `__dict__` |
| `C = 5` then `C()` | abort `TypeError` at the use |
| `P = Q` (class to class) | **correct**: `p = P()` gives `obj:Q` and `Q.m`. Dispatch is value-based, not name-based, so rebinding a class name is not a hole |
| `isinstance(x, obj)` | abort `TypeError`, which is why a user `__instancecheck__` is unreachable |
| `__subclasshook__`, `__reduce__` | unreachable: they need `ABCMeta` and `pickle`, and imports are rejected |
| user `__bool__`, `__len__`, `__eq__`, `__getitem__`, `__iter__` | `error-guard` obligation naming the exception the body raises, e.g. `truth truthiness: code -> KeyError` |
| user `__get__` / `__set__`, a function as a class attribute | rejected `class-body-stmt` — a class body admits methods, annotated fields, `__slots__` and docstrings only |
| a field assigned on one branch of `__init__` | `init-conditional` plus `uninit-field` obligations at the read |
| `True + True`, `True & False` | correct tags, so the `bool`-subclasses-`int` operator-priority trap is not tripped |

`object.__setattr__(o, ...)` is refused as `unmodeled-scalar-constructor` rather
than by a rule named for it, so it would reopen if `object` were ever admitted.

## 2. The class graph is fixed at declaration

Dispatch tables are derived from class declarations. If the MRO or the class a
name denotes can change, the tables describe a program that no longer exists.

| rule | rejected | why |
| --- | --- | --- |
| `metaclass-keyword` | any `metaclass=` other than the default | a metaclass can rewrite bases and the namespace before the class exists, and may define `mro()` — which can *drop declared bases*, so a base is not even a lower bound. Relaxable to metaclasses fully evaluable at admission |
| `class-decorator` | decorators on a class | a decorator can rewrite the class body or return a different object. Relaxable to decorators statically evaluable at admission — `@dataclass` with known arguments is the motivating case, and is admitted |
| `non-static-base` | *"base of class N is not a static name"* | a computed base means a computed MRO |
| `unsupported-base`, `unbound-base` | a base that is not an admitted class, or not bound at the declaration | the same, for bases that cannot be resolved. `unbound-base` is a forward reference, which CPython answers with `NameError` at the `class` statement |
| `invalid-mro` | *"no consistent C3 MRO for bases …"* | CPython raises `TypeError` here, so accepting it would model a program that cannot be built |
| `duplicate-class` | two `class` statements binding the same name | the later declaration replaces the earlier one at runtime, but the class table is keyed by name and resolves to the first match, so the second would be invisible. Two classes of one name are two tags the model cannot tell apart — see the measurement below |
| `nested-class` | a class inside a function | the shape would depend on runtime state at the definition site |
| `nested-function` | a `def` inside a `def` | a closure captures state, so the callee is not a static name |
| `reflected-dunder` | `__iadd__` and the other in-place operator methods | *"require the augmented-assignment protocol"* — a distinct dispatch shape not modelled |

`POMAD.md` is the design for lifting the first two: an order domain for uncertain
MROs, which is what would let decorators and metaclasses in with a bounded
candidate set rather than a fixed order.

## 3. A name denotes what it declares

| rule | rejected | why |
| --- | --- | --- |
| `shadowed-builtin` | binding a name the analyzer gives builtin semantics | the rule for `len` is the rule for the builtin; if `len` can be rebound the rule is describing something else |
| `global-stmt`, `nonlocal-stmt` | `global` / `nonlocal` | a write escapes the frame the analysis is threading |
| `import`, `import-star` | any import | an imported body is not analysed, so a call into it would need a contract stating its result, raises and write set. That contract language does not exist yet — see `RECURSION_CONTRACTS.md`. This is the single most valuable rule to lift |
| `lambda` | `lambda` | an anonymous callable is not a static dispatch target |

## 4. The value universe is closed, and identity is not part of it

| rule | rejected | why |
| --- | --- | --- |
| `unmodeled-scalar-constructor` | runtime `bool()`, `int()`, `float()`, `complex()`, `object()` | *"admitted only in annotations and isinstance."* Their conversion semantics are not modelled, so a runtime call would invent a value the datatype does not describe |
| `identity-comparison` | `is` / `is not` against anything but `True`, `False`, `None` | identity is not a function of a value. Within one code object constants are deduplicated, so `1000 is 1000` is `True`, while `c = 1000; c is int("1000")` is `False`; small ints and some strings are cached, so `5 is int("5")` is `True`. Modelling that means modelling CPython's constant pool. Immutable scalars are therefore given **no heap location**, which is sound precisely because immutability makes their aliasing unobservable — except through `is` and `id`. So `id` is banned and `is` is confined to the three singletons, where the language guarantees exactly one object |
| `unsupported-node` | any AST node with no lowering | fail-closed: a node the checker does not recognise is refused rather than ignored |

## 5. Hash and equality must agree wherever a value can be a key

| rule | rejected | why |
| --- | --- | --- |
| `hash-eq-contract` | *"defines `__eq__` without `__hash__`"* (or the reverse) | *"instances would break the hash/eq contract at key positions."* Two objects that compare equal must hash equally, or dict-key reasoning is wrong |
| `unfrozen-dataclass` | `@dataclass` without `frozen=True` | *"the generated `__eq__` sets `__hash__ = None`, breaking the hash/eq contract."* A frozen dataclass over hashable fields inherits the tuple contract by construction, so the check is syntactic — frozen, generated methods, hashable fields — rather than behavioural. `frozen=True` is enforced by a generated `__setattr__`, and the bypass (`object.__setattr__`) is already rejected by `hook-override`, which is what makes it actually immutable. Update-shaped code is served by `dataclasses.replace`: a fresh object per change, trivially sound |

The staged path for non-frozen dataclasses is to admit them with `==` on their
operands rejected — one dispatch row, giving field reads and writes with no
equality machinery — and only then generate per-shape heap-equality predicates if a
workload needs structural equality over mutable records, accepting the
invalidation churn that costs.

## 6. The exception hierarchy is static

| rule | rejected | why |
| --- | --- | --- |
| `non-exception-class` | a `raise` or `except` naming a class that is not a `BaseException` subclass | CPython raises `TypeError`; handler matching walks the exception MRO, so the class must be in it |
| `handler-name-collision` | `except ... as e` where `e` is used elsewhere in the same scope | the handler target is unbound when the handler ends. If the name is live elsewhere, that cleanup would destroy a binding the program still uses |

## 7. Control flow must be analysable without a summary

Every call is inlined, so anything that cannot be inlined has no sound treatment.

| rule | rejected | why |
| --- | --- | --- |
| `recursive-call` | direct or mutual recursion | the callee is already on the stack, so it would need a summary. Measured: assuming the declared return annotation lost both the deeper levels' writes and the base case's raise. `RECURSION_CONTRACTS.md` |
| `stub-without-return-annotation` | `def f(...): ...` with no `-> T` | a body-less function's declared types *are* its specification, so it must have one. Returning `any` instead would be sound and invisible |
| `multi-generator-comprehension` | more than one `for` in a comprehension | the encoding evaluates the body at a representative element and lifts the property pointwise; a second generator makes the provenance mapping no longer a function of one index |
| `with-stmt` | `with` | the context-manager protocol is a distinct completion shape |
| `match-stmt` | `match` | *"match is outside the subset"* — pattern binding is a distinct target form |
| `walrus` | `:=` | a binding inside an expression, so evaluation order and scope stop matching the statement model |
| `starred-arg` | `*args` at a call site | *"`*args` at a call site"* — argument binding is by signature; a splat makes arity dynamic |
| `async-construct` | `async def`, `await`, `async for`, async comprehensions | a coroutine's completion is not one of the five |
| `function-decorator` | decorators on a function, except `@property` and `@name.setter` on methods | the same reasoning as class decorators, and the two exceptions are statically resolvable to a field access |

A restriction worth recording that is **not** yet enforced: a function applied
inside a comprehension body must not mutate its arguments or anything outliving
one element's evaluation. The lifted-property encoding is sound only if evaluating
the body changes nothing, and an effectful body can prove a false property that
the unrolled form refutes. Today the subset reaches this indirectly — imports are
rejected, so a comprehension body can only call functions whose bodies are
inlined and analysed — but there is no rule named for it, and there should be one
before imports are admitted.

## 8. `super()`: admitted in one shape

### Why `super` is not analysable in general

`super` is a builtin that returns a **proxy object**, and almost nothing about it
is decided where you read it. Four separate things make the general case
intractable, and each one is a reason the admitted shape is as narrow as it is.

**It is a value, not a call form.** `super()` evaluates to a `super` instance
that can be stored, passed, returned, or aliased. `s = super(); s.__init__()`
puts an attribute lookup on a proxy whose binding target is discovered at the
lookup, so the dispatch site is no longer syntactically identifiable. Every rule
in this document that pins a dispatch site to a program point fails on that.

**Its target is not a function of the enclosing class.** A zero-argument
`super()` searches the MRO of `type(self)` starting after the class the call is
*written in*, and those give different answers. Measured against CPython with
`Left(Base)`, `Right(Base)`, `Bottom(Left, Right)` and `super().m()` inside
`Left.m`:

```
Left().m()    == 11    -- super() reached Base.m
Bottom().m()  == 111   -- super() reached Right.m, not Base.m
```

So there is no "the parent" to resolve to. Resolving against `Left`'s declared
base would give `Base` both times and silently skip `Right` — a missing arm,
which is a soundness defect rather than a precision one.

**The two-argument form makes the owner a runtime expression.**
`super(pick(flag), self)` chooses where the search starts at run time, so even
the *starting point* of the MRO walk is not statically known.

**The zero-argument form depends on a compiler-inserted cell.** It has no
arguments at all; CPython makes it work by giving any method that mentions
`super` an implicit `__class__` free variable and by taking the receiver from the
frame's **first positional argument** — whatever that argument is named. Both
inputs are frame introspection, which is the same mechanism `sys._getframe` is
banned for. That is also where the one soundness defect in the first
implementation came from, recorded below.

And there is no interface contract to lean on. Python imposes **nothing** on
`__init__` signature compatibility across a hierarchy: measured, a subclass
`__init__` may take entirely different parameters, a mismatched
`super().__init__(..)` is a `TypeError` only *when called*, and mypy `--strict`
reports an incompatible `meth` override while saying nothing about an
incompatible `__init__` — constructors are exempt from its Liskov check. So a
delegating call cannot be checked against a declared interface; it has to be
checked against the resolved body, which means resolving it exactly.

### What is admitted

Inheritance is admitted, so cooperative delegation has to be. Exactly one shape
qualifies, and it is the one where all four problems above disappear:

> a **zero-argument** `super().m(...)`, **immediately called**, inside a **method
> whose first parameter is `self`**, in a class whose **whole MRO is user code**
> terminating at `object`.

| rule | rejected | why |
| --- | --- | --- |
| `super-form` | `super(C, self)`; `super()` outside a method; `super()` in a method whose first parameter is not `self` | the two-argument form names the owner as a runtime expression; outside a method there is no owner, so no MRO suffix to search; and the first-parameter condition is what lets the receiver be read from the name `self` instead of from the frame |
| `super-builtin-base` | any class taking part in delegation whose MRO continues into a builtin base | `ClassInfo.mro` holds user classes only, so the chain has no next definer once it leaves user code. Delegating to `ValueError.__init__` would mean modelling what that constructor does to the instance, which is not modelled |
| `banned-builtin` | `s = super()`, `super().x` without a call, bare `super` | these reach the callee through the ordinary name path, where `super` is refused already. No new rule was needed: the carve-out in the `Call` lowering admits exactly the immediate-call shape, and the proxy-as-a-value case simply does not fall into it |

The residual risk is therefore not "does the proxy behave as expected" but only
"is the resolved target the one CPython would pick", and that is decided per
receiver tag rather than assumed.

### How it resolves

The owner is carried through lowering as the synthetic receiver
`@super:<Owner>` — the same `@`-prefixed convention already used for `@get:f`
and `@set:f`, and `@` cannot collide with a Python identifier. Because the target
depends on the receiver and not on the owner, nothing is resolved at lowering:
`resolveMethodAfter` does the walk during analysis, per receiver tag, so the site
is an ordinary dispatch with one arm per candidate class.

```
call super().m(..): obj:Left->Base.m after Left | obj:Bottom->Right.m after Left
```

Falling off the end of the chain means `object` is next, whose `__init__` accepts
no arguments and does nothing; that is the one case completing normally there.

Two consequences. Cooperative multiple inheritance conventionally threads
`**kwargs`, which `starred-arg` rejects, so only explicit-argument delegation is
expressible. And `super()` edges contribute nothing to the recursion call graph:
they ascend a finite MRO strictly, so they cannot close a cycle, while treating
them as edges made `super().__init__()` inside `Leaf.__init__` read as
self-recursion.

### The defect the first implementation had

Worth recording, because it is what the first-parameter condition exists for and
because of how it failed. `super()` takes its receiver from the frame's first
positional argument; the implementation reads the binding named `self`. With
`def m(this)` that binding is unbound, so the dispatch loop found no arm and the
call returned **bottom** — a claim that the method has no normal completion.
Measured: `Sub().m()` produced no value and filed **no obligation and no
violation**, where CPython answers 11.

That is the worst failure mode available, not a merely wrong answer: bottom makes
admitted code unreachable, and unreachable code discharges every later obligation
for free. It is now `super-form`, and `admission/reject_super_first_param.py`
pins it.

The `super-builtin-base` check has the same origin. It runs over every class that
could *be* the receiver rather than the class the call is written in, because a
subclass can splice a builtin into the chain between the owner and `object`:
`class Sub(Mid, ValueError)` sends `Mid`'s `super()` into `ValueError` even though
`Mid`'s own MRO is clean.

### What it fixed

`checkInitializedFields` reads the heap after `__init__` runs rather than the
subclass body, so delegation discharges the initialization obligation with no
special case: `super().__init__(3)` then reading the inherited field gives
`lit=3`, where the non-delegating version reports `init-missing` and
`uninit-field` and CPython raises `AttributeError`.
